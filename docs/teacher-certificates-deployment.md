## Настройки

- На backend установить зависимости из обновлённого `requirements.txt`; вместе с кодом доставить каталог `assets/fonts` и его лицензии.
- Задать `PUBLIC_CERTIFICATE_BASE_URL` реальным origin frontend, например `https://<домен-приложения>`, без префикса пути; приложение размещается в корне адреса. QR ссылается на `<адрес>/certificates/<случайный-токен>`. Значение примера следует заменить. Публикация с локальным адресом допустима только в QA.
- На web-хостинге frontend сохранить SPA fallback на `index.html` для прямого открытия `/certificates/:token`, `/teacher-certificates` и `/my-certificate`.
- Убедиться, что API доступен из frontend по HTTPS и загружает изображения и PDF с действующими HTTP-заголовками. В публичном маршруте отсутствует требование авторизации.

## Миграция

Новый файл: `roboman_back-main/migrations/20261008_001_teacher_certificates.sql`. Миграция добавляет отдельную сущность; прежние преподаватели, назначения и занятия не заполняются и не изменяются.

Требуется MySQL 8.0.16+ для CHECK-ограничений. Проверенный SHA-256: `2cd3c9aec1e1d735a76c40d6a2191c6cbf573df1be8f4a4b70146a44990ab500`.

Перед применением проверить состояние `schema_migrations` и соответствие checksum уже применённых миграций, а также наличие таблиц преподавателей и пользователей с совместимыми ключами. Сделать резервную копию целевой базы и убедиться, что она восстанавливается. Новые экраны включать после миграции и настройки backend.

Выполнять runner из каталога backend, задав все параметры подключения явно:

```sh
DB_HOST='<целевой хост>' DB_PORT='3306' DB_USER='<пользователь миграции>' \
DB_PASSWORD='<пароль>' DB_NAME='<целевая база>' \
python scripts/apply_migrations.py
```

Runner читает все миграции, пропускает зарегистрированные с совпадающим checksum и применяет неприменённые. До запуска необходимо проверить, что неожиданно неприменённых старых миграций нет. При текущем применении использован отдельный целевой скрипт вне репозитория с проверкой целевой БД, checksum, advisory lock и выполнением только нового CREATE TABLE; результат зарегистрирован в обычной `schema_migrations`.

MySQL DDL выполняет неявный commit. При ошибке нельзя считать rollback восстановлением схемы: сначала проверить фактическое состояние и завершить применение либо восстановить резервную копию. Существующие строки сертификатов при последующем rollback кода сохранять; не удалять таблицу с выпущенными документами.

## Проверка после применения

1. Войти администратором, открыть раздел сертификатов; исходно сертификаты не создаются автоматически.
2. Создать согласованный реальный сертификат, заполнить описание, образование и фото, опубликовать.
3. Открыть его ссылку в браузере без входа. Отсканировать QR, проверить frontend-домен, ФИО и назначенные сады.
4. Войти связанным преподавателем; проверить «Мой сертификат», PDF и отсутствие чужих документов.
5. Проверить PDF и ZIP выбранных действующих документов, кириллицу и ссылки.
6. Для согласованного тестового документа проверить отзыв и повторную публикацию. Использовать синтетические данные для destructive QA, не реальные выданные документы.

## Коммиты и push

После успешного согласованного применения миграции выполнить отдельные коммиты в `roboman_back-main` и `roboman_front-main`. Перед коммитом просмотреть diff, исключить локальные QA базы, журналы, фотографии и credentials. Проверить ветки и актуальность remote main; не выполнять force push. Затем push main каждого репозитория по инструкции пользователя.

Выпуск кода на сервер и smoke-проверки должны учитывать новые backend-зависимости и настройку публичного origin. Этот этап не считается выполненным одним только push; следует проверить действующую процедуру выпуска проекта.
