# Сертификаты преподавателей: реализация и проверка

Дата: 8 октября 2026 года. Разработка и локальная приёмка завершены. После отдельного разрешения пользователя новая миграция применена к prod-БД; код публикуется отдельными коммитами в main backend и frontend. Настройки хостинга в этом этапе не изменяются.

## Результат

- Отдельная сущность `teacher_certificates`: один документ на преподавателя, постоянные уникальные номер и публичный token, фотография, образование, описание, дата выдачи, состояние и версия изменений.
- Имя берётся из текущей карточки преподавателя. Сады берутся из активных назначений; история занятий не считается текущим закреплением.
- Публичная страница `/certificates/:token` доступна без авторизации, включая браузер с истёкшей сессией. Она содержит фото, ФИО, образование, описание, сады, номер, дату и QR.
- OWNER создаёт и редактирует документы, загружает фото, публикует и отзывает, скачивает PDF и ZIP выбранных действующих сертификатов. Действие доступно также из таблицы преподавателей.
- TEACHER видит «Мой сертификат», копирует ссылку и скачивает собственный действующий PDF. BRANCH не имеет доступа к закрытым экранам и API сертификатов.
- Черновик публично возвращает 404. Отозванный сертификат и опубликованный документ уволенного преподавателя возвращают 410 без персональных данных; закрыт также отдельный URL фото. Отпуск не отменяет документ.
- PDF формируется на сервере: кириллица, фото, QR и кликабельная ссылка, полное сохранение длинного текста. Обычный профиль с образованием и двумя садами помещается на одну страницу. ZIP содержит отдельные PDF с именами по уникальному номеру, максимум 100 документов.
- Ссылки и QR используют только настроенный серверный origin. Фото проверяются по фактическому содержимому и нормализуются в JPEG; метаданные удаляются. Параллельные изменения защищены `revision`.

Принятый вариант прав: описание, фото и публикацией управляет администратор; преподаватель просматривает и скачивает. Учебное заведение и направление необязательны. Изменение этих правил — отдельное уточнение требований.

## Основные файлы

Backend: `blueprints/teacher_certificates.py`, `certificate_pdf.py`, `assets/fonts/`, `tests/test_teacher_certificates.py`, `scripts/verify_teacher_certificates_mysql.py`; регистрация маршрутов в `main.py`, зависимости в `requirements.txt`.

Frontend: `src/pages/Certificates/`, `src/services/certificateService.js`; публичный маршрут вынесен за `AuthProvider`, добавлены закрытые маршруты, пункты навигации и действие в таблице преподавателей. Тесты проверяют маршруты, права, редактор, фото, конфликты версий, ссылки и экспорт.

ТЗ, декомпозиция, этот отчёт и инструкция публикации сохранены также в `roboman_back-main/docs/`. Документация frontend находится в `roboman_front-main/docs/teacher-certificates.md`.

## Команды повторной проверки

Backend, из `roboman_back-main`:

```sh
DB_HOST=127.0.0.1 DB_PORT=13327 DB_USER=root DB_PASSWORD='' \
DB_NAME=roboman_certificates_qa_none \
.venv/bin/python -m unittest discover -s tests

.venv/bin/python scripts/verify_teacher_certificates_mysql.py \
  --socket /tmp/roboman-certificates-qa.sock \
  --artifacts ../outputs/certificates-qa
```

Первая команда запускает тесты с подменёнными соединениями; схема `roboman_certificates_qa_none` не требуется. Вторая команда создаёт собственную временную синтетическую схему и удаляет её. Для второй команды нужна работающая отдельная локальная MySQL, а для проверки QR в QA-окружении — `zxing-cpp`; эта библиотека не является runtime-зависимостью продукта.

Frontend, из `roboman_front-main`:

```sh
CI=true REACT_APP_API_BASE_URL=http://127.0.0.1:5027/api \
npm test -- --watchAll=false --runInBand

REACT_APP_API_BASE_URL=http://127.0.0.1:5027/api npm run build
```

Во всех интеграционных запусках параметры БД/API заданы явно: дефолты прежнего проекта указывают на продуктивное окружение.

## Миграция и следующий этап

Файл: `roboman_back-main/migrations/20261008_001_teacher_certificates.sql`. Требуется MySQL 8.0.16+ для проверяемых CHECK-ограничений.

SHA-256: `2cd3c9aec1e1d735a76c40d6a2191c6cbf573df1be8f4a4b70146a44990ab500`.

Миграция создаёт одну новую таблицу, не изменяет существующих преподавателей и назначения. 8 октября она применена к prod-БД после разрешения пользователя. Полная SQL-копия проверена восстановлением в отдельную локальную схему; новая миграция успешно проверена на этой копии. В prod через новое подключение подтверждены запись с указанным checksum, пустая таблица, 12 ограничений и сохранность схем прежних таблиц и миграционной истории. Журнал и backup находятся вне репозиториев в `.local-backups/teacher-certificates-20261008/`.

После миграции выполняются коммиты backend/frontend и публикация main согласно уточнённому поручению. Выпуск приложения дополнительно требует установки новых backend-зависимостей, реального `PUBLIC_CERTIFICATE_BASE_URL` без префикса пути и SPA fallback frontend. Эти настройки хостинга в текущем этапе не меняются.
